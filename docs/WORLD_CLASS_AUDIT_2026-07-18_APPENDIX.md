# Appendix — Per-Dimension Audit Detail


## Architecture & Modularity


**Distance to world-class: FAR**


Real extension seams exist (data/providers/ trait-based MarketDataProvider registry, a 128-variant AppCommand bus, a working ComponentTheme trait-abstraction pattern in ui_kit) and the team demonstrably closes out dead parallel implementations when prioritized (commit 79b6ebec deleted a dead order-enum + 8 unadopted widget facades, ratchet-verified) and has built a genuinely mature CI quality-gate (dev/quality_gate.py + .github/workflows/quality-gates.yml) that the 2026-07-03 ARCHITECTURE_AUDIT.md's "F" CI grade no longer reflects. But the domain model is not separated from rendering: chart/renderer/gpu.rs (9,809 lines) hosts the Chart struct (246 fields) and Watchlist struct (148 fields) and is imported by 147/462 files (32%) across every other module -- foundation, persistence, data feeds, design_system, ui_kit all reach up into the renderer for domain types. This produces a genuine circular dependency (chart/ imports data/ in 24 files; data/feeds/ imports chart::renderer::gpu in 11 files -- e.g. drawings_feed.rs calls gpu::auto_draw_config() directly), which is almost certainly why the single-crate structure (_scaffold, 462 files, ~195K lines, 79 deps) has never been split. Of six migrations ARCHITECTURE_AUDIT.md flagged stalled, two are now genuinely resolved by deletion, one is a mature documented decision not neglect (core.rs's render_chart_pane, ~9,542 lines, "DEFERRED INDEFINITELY" per PANE_RS_SPLIT_PLAN.md on hot-path perf grounds, backstopped by a 1,067-scenario corpus), and three remain live: state-store dual-write, the canonical chart/state layer (still module-wide dead_code-allowed), and shallow AppCommand adoption (CI's own baseline counts 266 direct mutations in ui/; I found 38 in watchlist_panel.rs alone with zero AppCommand:: use). The indicator system is the clearest symptom of the missing domain seam: IndicatorType is a flat enum inside gpu.rs itself, matched 38 times there and 31 times in core.rs -- adding one indicator requires editing both god files, directly undercutting the "extensible via vibe-coding" differentiator. Net: a foundation with working seams in places that prove the team knows the right pattern, but the load-bearing domain types still live inside the render/window-loop file, blocking both a plugin-style indicator/pane system and a compile-time crate split.


**Strengths (protect these):**

- data/providers/ is a clean trait-based extension seam: MarketDataProvider: Connection (data/providers/provider.rs:61) with mock.rs, replay.rs, fallback.rs, http_fallback.rs, ib.rs, apex_data.rs, crypto.rs as swappable implementations -- exactly the pattern needed to add a new broker or data vendor without touching a god file.
- ui_kit/widgets/theme.rs deliberately defines a ComponentTheme trait so widgets depend on an abstraction instead of chart_renderer::gpu::Theme directly, with explicit code comments recording this as an intentional anti-coupling decision -- the correct dependency-inversion pattern already exists in-repo as a working template, it just hasn't been generalized to Chart/Watchlist/IndicatorType.
- A real, wired CI quality-gate (dev/quality_gate.py, dev/quality_baseline.json, .github/workflows/quality-gates.yml) ratchets unwrap-per-directory, dead_code allows, a file-size ceiling with named/ticketed grandfather exceptions (core.rs -> WS-E E4, gpu.rs -> WS-E E2, order_manager.rs -> WS-H #43), and command-bus-bypass count -- fail-on-increase on every push/PR via quality-ratchet + clippy-deny + build-matrix jobs. This is materially better than the 2026-07-03 audit's CI grade and is a strength worth protecting/extending, not rebuilding.
- The team follows through: commit 79b6ebec deleted trading/types.rs (a 4th duplicate order-enum) and 8 unadopted Wave-5 card facades, unified 11 scattered now_ms() implementations into one, and verified the cleanup against the quality ratchet (dead_code 47->46) rather than just claiming it done -- two of six previously-stalled migrations are genuinely closed, with evidence, not just re-labeled.
- src-tauri/docs/PANE_RS_SPLIT_PLAN.md is a mature, evidence-based engineering decision, not neglect: it explicitly declines to split the hot-path render_chart_pane function citing measured perf risk (inlining/cache locality), keeps the corpus (1,067 scenarios) as the standing regression net for any future staged extraction, and sets explicit rules (no mechanical refactors, benchmark-gated extraction only) -- this is the right way to say no to a refactor, and it should be the template for how other risky extractions in this codebase get evaluated.

## Data Pipeline


**Distance to world-class: FAR**


The transport/resilience layer (jittered backoff, per-route circuit breakers, the resilient_ws harness, subscription dedup/refcount) is genuinely well-engineered and heavily unit-tested -- better than most retail platforms ship. But two structural problems undercut the product vision. First, a subsystem purpose-built to heal reconnect gaps (SubscriptionManager.gap_fill_on_reconnect_all, wired into every WS feed) sends its replayed bars into a broadcast fanout that has zero live receivers at every production call site -- confirmed by the module's own doc (providers/mod.rs:20-28) admitting delivery flows through a different path (NATIVE_CHART_TXS) entirely, never this fanout. Every reconnect logs "replayed N bars after reconnect" while those bars are silently discarded, leaving a permanent, invisible hole in the chart's bar series -- the exact "reads as complete" defect class the brief calls out, one level deeper than the two already-known live_state issues. Second, market-data acquisition is hard-coupled to the owner's private homelab by default (a private, non-routable LAN IP is dialed unconditionally, bypassing DNS) with no functioning alternative: the IB provider is an admitted stub, the Replay provider is fully built but never instantiated anywhere, and the mock provider is explicitly test-only. For a "free, public, beats TradingView" product this is existential, not cosmetic -- an outside user gets, at best, the unofficial Yahoo v8 chart endpoint. Staleness-blindness is also broader than documented: the live quote cache has no timestamp field at all (a stronger version of the known snapshot bug), and it silently feeds the order-entry panel's compact DOM ladder -- which additionally fabricates fake depth-of-book sizes via a hash function with no "simulated" label, indistinguishable from the real top-of-book beside it.


**Strengths (protect these):**

- resilient_ws.rs (src-tauri/src/data/feeds/resilient_ws.rs:1-222,244-415) consolidates what used to be ad hoc per-feed reconnect code into one harness: jittered exponential backoff, idle-frame watchdog, LAN-aware connect, Shutdown-drain registration, and a documented Lagged-handling contract for subscribers -- a real architectural upgrade over the six bespoke feeds it replaced.
- Per-route-group REST circuit breaker (apex_data/rest.rs:18-135) keys breakers by path prefix so a failing poller (/api/snap) can't starve unrelated calls (/api/bars) -- verified by a dedicated passing test (rest.rs:1384-1411, tripping_one_group_does_not_open_another).
- Backoff (connectivity/backoff.rs) is a clean, allocation-free exponential+jitter+cap implementation with 5 passing tests covering monotonic growth, max-cap, max-attempts, reset, and jitter bounds.
- SubscriptionManager's refcount/dedup logic (providers/subscription_manager.rs:133-374) is correct and stress-tested under real multi-thread contention (896-972: 16 threads x 100 iterations with net-zero refcount assertions) even though its delivery fanout is unused in production (see findings).
- Split/dividend adjustment is requested explicitly and correctly scoped: apex_data/rest.rs:398-401 appends &adjusted=true for stocks only, with a comment explaining why options must never be adjusted -- a deliberate, correct design choice rather than an oversight.
- endpoints.rs centralizes what used to be ~15 scattered hardcoded homelab IPs into one honest, env-overridable, well-documented module (endpoints.rs:1-39) -- a real cleanup, not just a relocation.

## Trading Core


**Distance to world-class: FAR**


The order state machine (submit/cancel/modify lifecycle, WAL durability, modify-version coalescing, pair-integrity sweep, disconnect watchdog) is unusually mature and shows real incident-driven hardening. ## DOM & Order-Flow


**Distance to world-class: FAR**


The DOM ladder itself is a genuine surprise: it is not the naive mock the brief warned about. dom_panel.rs/gpu.rs implement real, tape-grounded per-price signals (order-flow delta, absorption, pull, big-print, buy/sell split) with an honest LIVE/SIMULATED badge and a stale-book trade guard that blocks one-click orders against the mock book — exactly the anti-deception discipline this audit rewards. But the dimension as a whole is FAR from Bookmap/Jigsaw parity because: (a) the flagship Bookmap feature — a DOM heatmap with depth history — does not exist at all (the ladder is frame-overwritten each update, no time axis, no persistence); (b) the "footprint" chart, the other headline order-flow differentiator, is 100% fabricated from OHLC shape (a gaussian centered on close/open) with zero tape grounding, yet renders confident, specific labels (ABSORPTION/REJECTION/EXHAUSTION) a live trader could act on — this is the exact "reads as complete, is fake" defect class the audit is hunting for, just in a new location; (c) the real DOM signals are quietly capped to the last ~100 trades per symbol (a hard ring-buffer cap) regardless of the 4000 the handler requests, so "session volume-at-price" actually resets every few seconds on a liquid future or index; (d) DOM trading UX has no ATM template system — the shift+click bracket is hardcoded to fixed tick offsets, while a working percentage-based bracket-template system already exists elsewhere in the code (right-click chart context menu) and simply isn't reused on the ladder; and (e) the CVD chart line silently blends real tape-derived delta with a synthetic close-position heuristic for older/no-trade bars with no visual distinction, unlike the DOM panel's own honest badge pattern. The latency path itself (WS thread → mpsc channel → next-repaint apply, a handful of short mutex locks) is architecturally tight and not a bottleneck.


**Strengths (protect these):**

- DOM panel shows an honest LIVE vs SIMULATED badge (green only when a live /ws/dom frame arrived within the last 2s) and a stale-book trade guard that only allows one-click bid/ask trading when is_live is true — the exact anti-deception pattern this audit is looking for, and it should be the template applied to the footprint/CVD gaps below (src-tauri/src/chart/renderer/ui/panels/dom_panel.rs:271-313, 657-662).
- Real order-flow signals — per-price delta, absorption, pull, big-print, buy/sell split — are computed from the server-side Lee-Ready aggressor tag on the live tape and wired end-to-end from feed to pixel, with clearly phase-labeled comments explaining the Jigsaw-style rationale (src-tauri/src/chart/renderer/gpu.rs:3085-3181; src-tauri/src/chart/renderer/ui/panels/dom_panel.rs:679-714).
- Position avg-price marker on the ladder derives dollars-per-point from the broker's own reported unrealized PnL divided by (mark - avg), so it's exact for stocks/futures/options with no hardcoded contract multiplier (src-tauri/src/chart/renderer/render/pane/core.rs:1510-1524).
- DOM trading UX (arm toggle before one-click fires, shift+click bracket, scroll-to-size, middle-click recenter, 200-tick scroll-drift clamp) closely mirrors TOS Active Trader / NinjaTrader SuperDOM feel and routes through the same guarded OrderManager path as the order panel (paper guard, risk gate, kill/halt re-check, journal) rather than a DOM-only shortcut.

**Findings:**


- **[P0] Footprint chart fabricates per-price buy/sell volume from OHLC shape, not tape data** (effort M)

  - *Gap:* This is the exact 'reads as complete, generates fabricated numbers' defect class called out in the audit brief (the seeded-RNG backtest precedent), now found in the one chart type that is supposed to be Apex's answer to Bookmap/Sierra footprint charts. There is no LIVE/SIMULATED-style badge on this overlay the way the DOM ladder has one, so a trader has no way to know it's synthetic.
  - *Fix:* Either (a) ground the footprint in the same live_state tape used by the DOM handler — bucket real prints by price within the bar's time range instead of a shape heuristic — with a fallback to the deterministic mock only for bars with no live trade history, badged the same way the DOM ladder badges SIMULATED; or (b) if real per-bar tape isn't available for older bars, gate the toggle to disable/gray out for any bar lacking real tape data instead of silently rendering the heuristic as if it were real.
  - *Verification:* ✅ CONFIRMED — Verified: gpu.rs:4330-4379 bar_micro_profile is pure gaussian(close/open)+direction math, no tape reference; core.rs:12308-12427 renders it as hard Δ/Buy%/Sell%/conviction/POC. Worse than claimed: live_state.rs:349-402 tracks real per-minute aggressor-side delta from live tape, used for bar-level Delta/CVD (gpu.rs:4402-4414, real-first w/ heuristic fallback) — footprint ignores it. Codebase has SYNTHETIC/LIVE/SIMULATED badge precedent (core.rs:11192, dom_panel.rs:271) absent here. Nit: wick labels derive from raw OHLC, not the split. P0 stands.

- **[P1] DOM volume/absorption signals capped at last ~100 trades per symbol, not the session** (effort M)
  - *Evidence:* live_state::push_trade caps tape_by_symbol at a hard 100 entries per symbol: `entry.push_back(t); while entry.len() > 100 { entry.pop_front(); }` (src-tauri/src/data/feeds/apex_data/live_state.rs:373-377). The DOM handler calls `crate::apex_data::live_state::tape_for(&symbol, 4000)` expecting up to 4000 trades to aggregate volume-at-price, big-print threshold, and the absorption/pull frame-to-frame comparison (src-tauri/src/chart/renderer/gpu.rs:3097), but tape_for can never return more than 100 regardless of the request.
  - *Gap:* The code comment at gpu.rs:3089-3094 calls this 'REAL session volume-at-price', but on any liquid instrument (ES, SPY, QQQ) 100 trades can print in a few seconds, so the ladder's volume/delta/absorption columns are really a sub-minute rolling window that keeps resetting, not a session profile. This directly undercuts the credibility of the absorption/pull/big-print signals during active tape, and would mislead a trader into thinking a level has 'absorbed' a full session's flow when it has only seen the last few seconds.
  - *Fix:* Raise the per-symbol tape cap to match what the DOM handler actually needs (or maintain a separate session-long price-bucketed volume aggregate keyed on the same tick grid, updated incrementally per trade instead of re-scanned per DomLevels frame) so 'volume' on the ladder means what its badge implies.
  - *Verification:* ✅ CONFIRMED — Verified: live_state.rs:373-377 hard-caps tape_by_symbol at 100 (VecDeque::with_capacity(100), pop_front while len>100); tape_for() :430-437 returns min(q.len(),max), so the 4000 requested at gpu.rs:3097 is capped to 100. Misleading "REAL session volume-at-price" comment at gpu.rs:3089-3091; absorption/pull logic (gpu.rs:3137-3171) consumes this same capped data. A correct session-VAP path exists (volume_profile_from_vap, gpu.rs:4245, backend-sourced) but feeds the main-chart profile, not the DOM ladder. P1 is appropriate.

- **[P1] DOM bracket is hardcoded 10t/20t, ignores the existing ATM-style template system** (effort M)
  - *Evidence:* `const STOP_TICKS: f32 = 10.0; const TARGET_TICKS: f32 = 20.0;` fixed for every symbol and every trader (src-tauri/src/chart/renderer/render/pane/core.rs:1642-1643), and the OrderIntent built for the DOM bracket hardcodes `trail_amount: None, trail_percent: None` even though `ManagedOrderType::TrailingStop` exists in the order type enum (order_manager.rs:405).   - *Verification:* ✅ CONFIRMED — All facts verified. core.rs:1642-1643 hardcodes STOP_TICKS=10.0/TARGET_TICKS=20.0 in dom_bracket handler; its OrderIntent (1654-1661) sets trail_amount/trail_percent None, order_type Limit only, never uses TrailingStop (order_manager.rs:405, a live variant used elsewhere). pane_context_menu.rs:220-256 shows a working percentage BracketTemplate create/delete UI wired to chart.bracket_templates — the DOM path never references it, confirming two disjoint bracket paths. - **[P2] "Bid/ask imbalance" field computes no actual size ratio, just above/below-price sign** (effort S)
  - *Evidence:* `let imb = if ia { 1.0 } else { -1.0 };` where `ia = price > current_price + tick_size*0.5` (src-tauri/src/chart/renderer/ui/panels/dom_panel.rs, ~line 630, feeding `.imbalance_fill(imb)`). dom_row.rs then treats `imbalance: f32` as a -1..1 magnitude for the ghost-fill wash (src-tauri/src/chart/renderer/ui/lists/rows/dom_row.rs:136-254), but since the caller only ever passes exactly +1.0 or -1.0, the 'magnitude' is always maxed and the signal conveys nothing beyond 'this row is on the ask side of price' — which the BID/ASK columns already show.
  - *Gap:* The audit brief explicitly calls out 'bid/ask imbalance signals' as a gap to assess vs Bookmap/Sierra, where imbalance means the resting size ratio at a price (e.g. 4x more bid than ask). That signal does not exist here despite a same-named field suggesting it does.
  - *Fix:* Replace `imb` with an actual ratio, e.g. `(bid_size - ask_size) / (bid_size + ask_size).max(1)`, computed per-row from the level's own bid_size/ask_size (already available as `bs`/`ask` at that call site) instead of the static above/below-price sign.

- **[P2] No DOM heatmap-with-history — Bookmap's signature feature does not exist** (effort XL)
  - *Evidence:* The DomLevels handler replaces `self.dom.levels` wholesale on every frame with no retained history and no time dimension (src-tauri/src/chart/renderer/gpu.rs:3085-3181); the only 'heatmap' panel in the codebase is an unrelated market/sector dollar-volume treemap fed from daily grouped bars (src-tauri/src/chart/renderer/ui/panels/heatmap_pane.rs:1-8), not a liquidity heatmap.

  - *Fix:* Persist a rolling ring buffer of (timestamp, price-bucket, bid_size, ask_size) snapshots per symbol (bounded, e.g. last 10-20 min at the DOM's own update cadence) and add a heatmap render mode to the DOM pane or a companion pane that paints it as a scrolling column strip, using the same tick-bucket alignment already established for volume-at-price.

- **[P2] No iceberg/reload detection; DOM feed source is MBP-only with no seam for a real L3 provider** (effort L)
  - *Evidence:* dom_feed.rs is a single-source client of apex-data's `/ws/dom` (or the unified `/ws/v2` depth topic), parsing only a flat bids/asks array with price+size — no order-count, no per-order queue data, no book-event stream that iceberg/reload detection needs (src-tauri/src/data/feeds/dom_feed.rs, entire file). No mention of Databento, Rithmic, or dxFeed anywhere in the codebase, and no provider-agnostic depth interface exists (contrast with data/providers/ having a registry pattern for other data types).
  - *Gap:* Reload/iceberg detection (repeated size replenishment at a price after each fill) requires order-level (MBO) or at minimum trade-linked depth events; IBKR's TWS API reqMktDepth is aggregated market-by-price, which structurally cannot produce this signal no matter how it's post-processed client-side. This is a data-sourcing gap, not a code gap, but the codebase has no seam prepared for plugging in a second depth provider when one becomes available.
  - *Fix:* Define a `DepthProvider` trait mirroring the existing `data/providers` registry pattern, with the current apex-data /ws/dom as the MBP implementation; when a Databento/Rithmic/dxFeed MBO feed is added it plugs in without touching dom_panel.rs or the gpu.rs signal suite, and iceberg/reload detection becomes a new signal computed only for symbols on the MBO path (flagged distinctly from the MBP-derived absorption/pull heuristics, which should stay labeled as proxies).

- **[P2] CVD chart line silently blends real tape delta with a synthetic OHLC-shape heuristic** (effort S)
  - *Evidence:* compute_volume_analytics computes per-bar delta as `realized_delta_in(...)` when available, falling back to `buy_ratio = (close-low)/range; volume*buy_ratio - volume*(1-buy_ratio)` for any bar lacking live trade history (src-tauri/src/chart/renderer/gpu.rs:4394-4415), then cumulatively sums both into one continuous `cvd_data` line with no marker for where real data ends and the heuristic begins (gpu.rs:4417-4422).
  - *Gap:* The DOM ladder in the same codebase demonstrates the right pattern (an explicit LIVE/SIMULATED badge) for exactly this real-vs-synthetic distinction, but the CVD chart series — read by traders as a session order-flow indicator — doesn't apply it, so a trader scrolling into history sees one uninterrupted line with no way to tell where it stops being real.
  - *Fix:* Either restrict the CVD line to only the live session (where realized_delta_in has actual coverage) and gray out/dash historical segments using the close-position proxy, or add a hover tooltip / legend note per-bar indicating real vs proxy, matching the DOM panel's existing badge discipline.

- **[P3] DOM ladder row lookup is O(visible_rows x levels) per frame via linear scan** (effort S)
  - *Evidence:* `let lv = levels.iter().find(|l| (l.price-price).abs() < tick_size*0.5);` inside the per-row render loop (src-tauri/src/chart/renderer/ui/panels/dom_panel.rs:593), re-scanning the full `levels` slice for every one of the ~40 visible rows every frame.
  - *Gap:* Immaterial today at ~40 rows x ~60 levels, but this pattern would not scale if depth is widened (e.g. for a future heatmap-history feature) or if the ladder moves to a higher-frequency update cadence.
  - *Fix:* Pre-index `levels` into a HashMap/BTreeMap keyed by the same tick-bucket integer used elsewhere in this file (dom_feed.rs already uses `(price*1000.0) as i64` bucketing) once per frame before the row loop, and look up by bucket instead of scanning.


**Highest-leverage move:** Stop the footprint overlay from fabricating order-flow labels off an OHLC shape heuristic — either ground it in the same live_state tape the DOM ladder already uses (a well-understood, already-solved problem in this same codebase), or badge/disable it exactly like the DOM panel's LIVE/SIMULATED pattern until it is. This is the single highest-severity item because it actively generates specific, confident, actionable-sounding signals (ABSORPTION/REJECTION/EXHAUSTION) with zero grounding in real trades, on a live-money terminal, and the fix pattern (honest live/synthetic disclosure) is already proven correct one file away in dom_panel.rs — making this as much a policy/consistency fix as a data fix.

## Quality & Testing


**Distance to world-class: FAR**


Apex Terminal has more test-infrastructure sophistication than most solo/small-team codebases (769 #[test] fns, a well-engineered quality_gate.py ratchet, and a 1067-scenario behavioral corpus with real lessons-learned rigor in dev/run_corpus.py). But the safety net has large, evidenced holes exactly where the audit's stated dominant defect class predicts: the corpus's own default-safe assertions (canvas_all_finite, viewport_sane) silently pass when a pane never loaded bars. This is not theoretical: the most recent recorded 1067/1067 GREEN run (dev/corpus_app.log, 2026-07-17) shows the DOM feed unreachable (apexibdata-api:5000 connection resets, repeated WebSocket errors) and the main ApexData feed stalling twice mid-run ("feed silent for >32s"), yet the verdict reported zero failures. The order-journal WAL (crash-recovery/orphan-detection, the mechanism live orders depend on after a crash) and the entire persistence layer (drawing_db, watchlist_db) have zero tests. 17 of 20 indicator compute functions have no golden-value correctness oracle.


**Strengths (protect these):**

- chart/renderer/trading/ (the order state machine) has real depth: order_manager.rs alone carries 79 #[test] functions covering transition matrix, WAL rotation, and risk boundaries per its own file header; broker.rs and inflight.rs add 17 more.

## Persistence & State Durability


**Distance to world-class: NEAR**


This dimension is bimodal. Order persistence (the store where a bug can lose real money) is genuinely excellent: an fsync'd, rotating, orphan-detecting WAL with hourly backups, a fail-closed kill-switch restore on corrupt control_flags.json, correct handling of the 'Rust statics don't Drop at exit' gotcha via an explicit shutdown marker, and PendingSubmit orders correctly demoted to Unknown (never falsely Working) on restart with a user toast. The general-purpose state::persistence layer (Persistable trait; atomic tmp+fsync+rename+dir-fsync; versioned envelope with migrate hook) is well designed and backs six wired+registered Store<T> aggregates plus plays.json and orders.json - more than docs/STATE_SYSTEM.md (stale since 2026-05-22) credits.

But drawings and watchlists have real, silent, user-facing durability holes. Drawing persistence depends on one blocking Postgres connect at startup with no retry; on failure the only trace is an eprintln! that never reaches the UI, and drawing_db::save()/load_symbol() then silently no-op for the rest of the session - a trader can annotate all day, see zero errors, and lose every drawing on restart. Drawings that exhaust 3 retries even when Postgres IS up land in an in-memory dead-letter queue nothing reads, logged via bare tracing macros instead of the toast-capable errors_sink used everywhere else. Watchlists have a parallel bug: load_watchlists()'s own comment promises a Postgres fallback that does not exist anywhere in the codebase - a fresh machine silently gets an empty watchlist. The one manual backup path, .xol export, is the single save site that skips atomic_write. And the 30s autosave (v3) vs explicit Save-Workspace (v4) are unsynchronized duplicate loaders, so a normal restart quietly loses pane-split/panel layout that an explicit save would keep.

None of this touches order money-safety, correctly the top priority - but drawings and watchlist context are exactly the daily-driver trust the product vision depends on, and the app can lose them without ever telling the user.


**Strengths (protect these):**

- Order WAL is production-grade: append-only JSON-lines, fsync'd per write, 10MB rotation with one kept generation, orphan-attempt detection wired at startup (order_manager.rs:72-78, journal/mod.rs:70-90), hourly backup thread with 24-generation pruning (journal/mod.rs:98-154). Real safety infrastructure, not scaffolding.
- Control-flags kill/halt restore is fail-closed on corrupt state (order_manager.rs:46-65): a truncated control_flags.json after a crash forces kill_engaged=true rather than silently disarming the safety interlock, and reports ErrorLevel::Critical so the toast pipeline surfaces it.
- state::persistence (state/persistence.rs) is a solid crash-safety primitive: write to <path>.tmp, flush, sync_all, rename, then fsync the parent directory - with unit tests for round-trip, version migration, and key-mismatch rejection.
- errors_sink (data/connectivity/errors_sink.rs) is a real, tested, single choke-point for surfacing failures: bounded ring buffer for a diagnostics panel, monotonic Prometheus counters, automatic severity-coded toast routing. WAL and persist_supervisor route through it correctly - drawing_db notably does not.
- Order restore from disk correctly distinguishes 'we know it's live' from 'we don't know' - PendingSubmit is demoted to Unknown (not Working) on cold start (order_manager.rs:2793-2831), with a user-visible toast rather than silently trusting stale state.
- The Store<T>/StoreRegistry/persist_supervisor mechanism has correct shutdown ordering - the supervisor is explicitly stopped before the final flush_all on window close (gpu.rs:7894-7897) so it cannot race a stale write in after the authoritative save - and is unit-tested for that ordering.

- **[P2] MarketDataProvider is a clean trait but not a real plugin surface — hardcoded chain + 29 UI files bypass it directly** (effort L)

- **[P2] Broker trait's arg structs bake in Interactive Brokers' conId model, leaking broker-specific identity into the abstraction** (effort M)
  - *Evidence:* trading/broker.rs: ContractDetails{ pub conid: i64, ... } (52-58), ComboLeg{ pub con_id: i64, ... } (203-207), and every submit_* method's HTTP-body construction resolves a con_id via resolve_con_id() before building the request (e.g. submit() at 332-336, submit_bracket() at 561-562).   - *Gap:* A broker without IB's integer contract-ID concept (Tradier/Tastytrade/Schwab/Alpaca, per the owner's own ApexBroker roadmap) has no natural conid to populate — it would need to synthesize a fake one or the trait/arg-structs need refactoring to a symbol-first shape.   - *Fix:* Generalize ContractDetails/ComboLeg's identity field to an opaque `provider_ref: String` (already how symbol/side/qty are carried) before the next broker integration, so IB's conId becomes one broker's implementation detail rather than the trait's vocabulary.

- **[P3] The two files most new features must edit are single monoliths (gpu.rs 9,809 lines; render/pane/core.rs 13,421 lines)** (effort L)
  - *Evidence:* wc -l confirms both sizes; indicator rendering, y-axis scaling, and per-kind visual branches for BB/KC/Ichimoku/PSAR/Supertrend are all scattered as `if ind.kind == IndicatorType::X` blocks within core.rs rather than behind any per-feature module boundary.
  - *Gap:* Any two contributors adding unrelated indicators or drawing tools in parallel are statistically likely to produce merge conflicts in the same giant file, and code review for a single indicator PR requires navigating an unrelated 13k-line file.
  - *Fix:* Not urgent to fix wholesale, but any new Indicator-trait refactor (finding above) should deliberately carve rendering into per-kind modules as a side effect.


**Highest-leverage move:** Formalize ONE real extension boundary end-to-end rather than polishing the two half-built ones. Indicators are the highest-value, most-tractable target: replace the IndicatorType enum-and-match sprawl (gpu.rs, indicators_panel.rs, indicator_editor.rs, render/pane/core.rs — ~140 sites) with a `trait Indicator { fn compute(&self, ohlcv) -> IndicatorOutput; fn params(&self) -> ParamSpec; fn render(&self, ...); }` plus an `IndicatorRegistry::register()` called once at startup. This collapses "add an indicator" from touching 6+ files including two monoliths down to implement-trait-and-register, kills the incremental-update NaN footgun by making the registry own a single dispatch point, and — critically — becomes the template for finishing what MarketDataProvider and Broker started (both already have clean trait shapes but no real registration mechanism and, for Broker, IB leakage in the arg types). Pair this with a real LICENSE + CONTRIBUTING.md documenting the register-in-N-places gotchas (SidebarState struct literals, the two DrawingKind enums) so the pattern doesn't have to be rediscovered by breaking the build again.
