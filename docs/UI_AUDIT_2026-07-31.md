## P0-1 — The mystery border: egui's default widget stroke was never overridden

**This is the single highest-value fix in the audit — one line.**

`widgets.noninteractive.bg_stroke` is **never assigned anywhere in the app**.
Exhaustive grep for `noninteractive` outside the playground returns only
*corner_radius* assignments:

- `chart/renderer/gpu.rs:7321` — corner_radius (inspector window only)
- `chart/renderer/inspector_window.rs:158` — corner_radius (inspector only)
- `chart/renderer/ui/style.rs:2802` — corner_radius

The main theme setup, `gpu.rs:5094 setup_theme()` (visuals block `5140-5224`),
explicitly sets `inactive` (5172), `hovered` (5179), `active` (5185), `open`
(5191), `selection`, and `window_stroke` (5205) — **but never
`noninteractive.bg_stroke`**. It therefore retains egui 0.31's `Visuals::dark()`
default: **`Stroke::new(1.0, Color32::from_gray(60))`** — a flat off-theme gray.

`style.rs:2797-2805` then applies `corner_radius = cr_sm` to `noninteractive`,
making that stray stroke **rounded**.

Everything consuming noninteractive visuals paints a faint gray rounded 1px line:
- `ui.group()` / `Frame::group(style)` (e.g. `panels/scanner_panel.rs:220`)
- **all 57 `ui.separator()` call sites** — top: `toolbar/chart_controls.rs` ×14,
  `panels/auto_chart_panel.rs` ×7, `panels/watchlist_panel.rs` ×6, `components/perf_hud.rs` ×6
- `Ui::indent()` left v-lines (`indent_has_left_vline` never disabled — 0 hits repo-wide)

**Fix:** set `style.visuals.widgets.noninteractive.bg_stroke` to `Stroke::NONE`
(or a theme hairline) in `gpu.rs` near line 5170. One line removes 57 off-theme
gray separators and every stray group outline.

**Session note:** hours were lost hunting this as a "PanelSection box" — the frames
in that path (`panel_section.rs:478`, `panel_empty.rs:72`, `side_panel_shell.rs:658`)
are all genuinely `Frame::NONE`. The outline never came from app code.

Secondary contributor (uncommitted, this session): `panel_list_row.rs` now paints a
rest-state capsule fill (`color_alpha(t.surface_border(), 18)`, inset 6px, radius 8)
behind **every** row, so a section body reads as a stack of faint rounded slabs. The
file's doc at `panel_list_row.rs:23` still claims "No stroke. No border." — now false.
Consider gating it or lowering alpha.

## P0-2 — 40 ui_kit widgets are permanently style-blind (`PortableTheme`)

`gpu.rs:5109-5112` stashes a **`PortableTheme`**, not the app `Theme`. `ui_kit`'s
`active_theme(ctx)` (`ui_kit/widgets/theme.rs:242`) returns that, and **40
parameter-less ui_kit widgets** call it (`button.rs:551`, `checkbox.rs:79`,
`switch.rs:58`, `slider.rs:71`, `tag.rs:238`, `toast.rs:112`, `progress.rs:60`,
`separator.rs:131`, `stepper.rs:239`, `trade_card.rs:132`, …).

`PortableTheme` overrides **none** of the per-style methods, so all 40 widgets get
`section_header_mono=false`, `cards_float=true`, `row_side_margin=0.0`,
`row_corner_radius=0`, `row_divider_alpha=0`, `row_height=26.0` — **regardless of
`style_idx`**. The design system does not reach them.

Related footgun: the `&T` blanket impl at `theme.rs:477-499` forwards only the 21
required methods + `shadow_color`. It does **not** forward `section_header_mono`,
`cards_float`, `row_side_margin`, `row_corner_radius`, `row_divider_alpha`,
`row_height`, `surface_raised`, `shadow_card`. Any instantiation where `T = &Theme`
silently reverts those 8 to defaults, with no compile-time signal.

**Fix:** stash the concrete `Theme` (or make `PortableTheme` carry the per-style
row/card/header tokens), and add the 8 missing forwards to the blanket impl.

## P0-3 — Typography: 70% of the app renders at 9–11px (the "scrunched/unreadable" complaint)

Token usage across production UI (626 token call sites):

```
font_sm (11px) 222 | font_xs (9px) 219 | font_md (13px) 74 | font_lg (16px) 37
font_2xs (8px) 28  | font_xl (22px) 18 | font_md_plus(14) 10 | font_xs_plus(10) 9
```

**441 of 626 sites (70%) are 9px or 11px.** Meanwhile the row the owner likes —
`lists/rows/watchlist_row.rs:312` — hardcodes `14.0–15.0`, i.e. **~40% larger than
the rest of the app**. That gap *is* the complaint, quantified.

Scale defects:
- `font_3xs()` and `font_2xs()` are both **8.0** (`ui_kit/style.rs:337` vs `:338`) — duplicate tier.
- `font_2xl` is aliased to `font_lg` = **16**, which is *smaller* than `font_xl` = 22
  (`chart/renderer/ui/style.rs:247`).
- `TextStyle` heading hierarchy is **inverted**: `HeadingMd`=22 > `Display`=20 >
  `HeadingLg`=16 (`ui/foundation/text_style.rs:47-49`).
- `TextStyle::line_height_factor` is computed for all 14 tiers and **never read**
  (`text_style.rs:36`, `:47-60`; `as_rich()` at `:65-71` ignores it) — the entire
  vertical-rhythm half is dead code.
- **Four competing scales**: ui_kit tokens, per-style `StyleSettings.font_*`
  (`style.rs:2205/2263/2321`), `design_system::Typography.size_*` (`builtin.rs:851`,
  incl. `15` and `48` which exist in no token), and raw literals.

`TextStyle` adoption is **~10%** (131 sites vs 1160 `.size(` sites); **0% inside
`ui_kit`** — 62 text-rendering ui_kit files, none use it).

Mono/proportional rule (`panel_key_value_row.rs:74`: label=proportional, value=mono)
is **inverted in the flagship row**: `watchlist_row.rs:343-348` renders the *symbol*
(a label) monospace and *price + change%* (numeric data) **proportional** — so columns
don't tabular-align. Panels overall run 87 monospace : 14 proportional.

## P1-2 — Token discipline: radii are the broken axis (21% compliance)

| Category | Literal sites | Token uses | Compliance |
|---|---|---|---|
| **Corner radii** | **172** | ~45 | **~21%** |
| Colors | 115 true hardcodes | — | — |
| Spacing | 49 | 1214 `gap_*()` | ~96% |
| Font sizes | 28 | 668 `font_*()` | ~96% |

The radius leak is the **positional** rounding arg — `rect_filled(rect, R, color)` —
which a `CornerRadius::same` grep misses: 135 `rect_filled` + 20 `rect_stroke`
literals. Of those 155: **87 are `0.0`** (permanently flush — wrong on
Aperture/Cadence) and **68 are non-zero** (permanently rounded — wrong on
Meridien/Mariner). **Both directions are broken.** Worst: `chart_widgets.rs` (8),
`dom_row.rs` (7 non-zero/18), `toolbar/dropdowns.rs` (6), `watchlist_panel.rs`
(4 non-zero/13), `heatmap_pane.rs` (4). Notably `side_panel_shell.rs:158` and
`split_tabs.rs:183` hardcode `CornerRadius::same(2)` on panel chrome — exactly what
`region_radius` exists for.

**Theme-blind panels (owner's "fixed colors no matter what theme"):**
`Theme` defines `rrg_leading/improving/weakening/lagging` (`gpu.rs:197-203`) tuned
for all ~19 themes — and both RRG panels ignore them:
- `panels/msg_rrg_panel.rs:301-309` — doc comment says "theme-aware", fn takes no
  `&Theme`, hardcodes all four quadrant RGBs.
- `panels/rrg_panel.rs:18-30` — `SECTOR_COLORS` const table (11 hardcoded RGBs);
  `:539` literal white crosshair (breaks on the 5 light palettes); `:189` gray fallback.

**Latent bug worth fixing now:** in `rrg_panel.rs:21,24,25,28` a codemod substituted
*alpha* tokens into the **blue channel** of RGB tuples:
`("XLE","Energy",(230,160,ALPHA_MUTED))`, `ALPHA_STRONG`, `ALPHA_LINE`, `ALPHA_DIM`.
Values coincide today, so it compiles and looks correct — but retuning any alpha
token silently changes sector hues.

Other shadow palettes: `components/layout.rs` (6× `Color32::GRAY` as *defaults* for
`dim`/`title_color`/`rule_color`), `components/headers_widget.rs:14-17`
(`FALLBACK_ACCENT/DIM/PANE_BG/PANE_BORDER` — dark-only), and `ui/style.rs:765-811`

## P1-3 — The Sx / recipe system is inert (dead abstraction)

The plumbing exists end-to-end, but only the **empty set** ever flows through it:

- `gpu.rs:5119-5132` — each frame, if no pack stashed recipes, installs
  `empty_recipe_arc()`.
- The only non-empty producer is `theme_pack_bridge.rs:217-220`, reachable **only**
  via an installed `.apextheme` bundle. Built-ins bypass it entirely
  (`theme_pack_bridge.rs:161-170` applies the colour axis only).
- `theme_studio.rs:333` installs `RecipeSet::new()` — empty.
- `StyleCtx::from_ctx` (`ui_kit/widgets/ctx.rs:102`) has **zero production call
  sites**; everything uses `from_theme`, which hardcodes `empty_recipe_arc()`
  (`ctx.rs:123`).

So `recipes.resolve(...)` always returns `default_sx` (`design_system/recipes.rs:97-105`).
Only **6 keys** are consumed at all (`row.list`, `row.list.selected`,
`section.header`, `tab.line.active`, `tab.pill`, `tag`) across 4 of ~95 widget files
— ~55 KB of spec machinery serving 6 always-default keys. The tests at
`recipes.rs:436-575` assert the *empty* path, i.e. they validate the inert behaviour.
The "canonical key registry" referenced at `recipes.rs:47` (`docs/migration/recipe-keys.md`)
**does not exist**.

**Decide:** wire it (ship built-in recipe sets + use `from_ctx`) or delete it.

### Corrected during the fix (findings that did NOT survive contact)

1. **The section-body outline is NOT `noninteractive.bg_stroke`.** A magenta
   3px probe on that stroke showed it painting only the rail-edge vertical — the
   faint outlines around each PanelSection body stayed grey. The `bg_stroke` fix
   is still correct and worth keeping (it was genuinely unset and off-theme), but
   it is **not** the cause of the section outlines. That source remains
   UNIDENTIFIED: `panel_section.rs` body frame, `panel_empty.rs`,
   `panel_list_row.rs` and `side_panel_shell.rs`'s `body_frame` are all provably
   stroke-free, and a magenta *fill* probe confirmed the outline coincides
   exactly with the PanelSection body rect. Still open.
2. **`region_frame` does NOT unconditionally stroke the nav's bottom edge.** It
   has two branches; for flush styles (`region_gap <= 0`) it is `Frame::NONE`
   with no stroke at all. Deleting the manual nav bottom border would have left
   flush styles with zero separation, so it was gated on `region_gap <= 0`
   instead — duplicate removed on tiled styles, boundary preserved on flush ones.
3. **The 14 `chart_controls.rs` separators are menu-section dividers inside
   `show_menu` popups, not inter-button dividers**, so the
   `button_group_enclosed()` suppression contract does not apply to them (the
   toolbar-row dividers it *does* apply to were already correctly gated). Left
   alone deliberately; gating them would have merged menu sections. One real fix
   made there: a trailing separator that painted with nothing below it when the
