## D1 — Archetype is a THEME PROPERTY with a USER OVERRIDE

`ShellProfile` (Stream S6: `NavStyle` / `DockStyle` / `RailSide`) is **absorbed
into `StyleSystem`** as a `ShellSpec` block. It does not become a separate axis
and it does not stay a parallel mechanism.

```
StyleSystem {
    shell: ShellSpec {
        nav:       NavStyle,
        dock:      DockStyle,
        rail:      RailSide,
        archetype: Archetype,   // the theme's DEFAULT
    }
}

Workspace { archetype: Option<Archetype> }   // user override, may be None
```

Resolution is one line, and deliberately the **same shape** as the colour and
dimension axes that are already proven:

```
effective_archetype = workspace.archetype.unwrap_or(active_style.shell.archetype)
```

### Why this and not the alternatives

- **Not a free third axis.** `ColorScheme × StyleSystem` is already 22 × 9. A
  third independent axis multiplies the untested surface again, and the
  certification work in `12-T5-CERTIFICATION` only vouches for six curated
  pairings. More importantly it would break the claim the whole package rests
  on: that a theme *is* a coherent design system. If "Aperture" stopped implying
  its mosaic, Aperture would mean only colour and dimension.
- **Not fixed pairings.** Users already expect to move panels; hard-locking
  layout to theme would be the one place the design system takes away a freedom
  the app currently has.
- **The override lives on the WORKSPACE, not the theme.** This matters: a user
  who picks a layout is expressing a preference about *this workspace*, not
  editing the theme. Putting it on the theme would make a personal choice
  contaminate a shared design artifact — and themes are exportable
  (`.apextheme`), so it would travel to other people.

### Consequence for `ShellProfile`

`docs/migration/shell-profile.md` stays the design reference for what
`NavStyle` / `DockStyle` / `RailSide` *mean*. It stops being a separate
selection mechanism — no independent `ShellProfile` store, no second resolver.
Its types move onto `ShellSpec`. `theme-authoring/README.md`'s reserved
`shell_profile` blob becomes the serialized `ShellSpec`, so the forward-compat
placeholder is honoured rather than orphaned.

**Owner of the overlap:** this package. S6 contributes the vocabulary; the
resolver, storage and precedence rule are owned here.

## D2 — Named presets in the main UI, full matrix in Theme Studio

The six certified pairings ship as **named presets** — the primary and default
way to choose a theme. The raw `ColorScheme × StyleSystem` matrix stays
available in Theme Studio.

Rationale: curation where most users are, freedom where they go looking for it.
This also keeps the certification claim honest — `12-T5` certifies six
pairings, and those six are exactly what the main UI offers. Combinations
reachable only from Theme Studio are explicitly uncertified, and that is fine
because the user got there deliberately.

Presets are the six from the capture set: Aperture, Cadence, Alto, Mariner,
Lucid, Meridien.

## D3 — Dashboards are WORKSPACE VIEWS, not shell modes

New archetype layouts register in the **existing workspace system** as views.
They do not restructure the root shell.

This is the recommendation `06-LAYOUT-ARCHETYPES` already made, and the reason
is decisive: shell modes would touch `core.rs`, which is sacred
(`src-tauri/CLAUDE.md`) and excluded from every design-system sweep. A
workspace view needs no core change, inherits persistence, and can be added and
removed per workspace.

`ShellSpec.archetype` therefore selects **which view is the default content**
for a workspace, plus the nav/dock/rail shape around it. It does not rewrite the
shell's structure.

Scope: all four editorial themes, not Lucid-first. The platform work is done and
the risk that justified a proof-first approach has largely been retired by
`12-T5` — the six systems already render distinctly from data.

## D4 — Aperture ships `border: none` literally

No borders on Aperture surfaces. Separation is carried by elevation, bevel tints
and background steps.

This is now cheap to honour rather than a stretch: `Edges`/`EdgesRef` (per-side
borders), `BevelSpec`/`BevelSpecRef` (inset hairlines) and the shadow-layer
stack all landed in M0–M3 specifically so a system could express separation
without lines. Falling back to a hairline would mean shipping the machinery and
then not using it in the one system designed around it.

If a specific dense-data surface turns out to genuinely need a boundary for
function rather than decoration, that is a **per-recipe** exception
(`card.dense`, say), authored and reviewed as such — not a global fallback.
